# Evidence — Phase C, weather layer (29/08/2026)

> *Written in Portuguese on 29–30/08/2026, translated into English on 01/09/2026. The
> English text is the normative version of this note; the Portuguese original stands
> unchanged in the repository history at commit `bf3fd90`.*

This note records the project's first real weather ingestion: the AgERA5 daily
reanalysis series from the Copernicus Climate Data Store and the hourly station
observations from IPMA, written to the `observations` table beside the field readings
and the satellite series, through the same HTTP routes.

Run on 29/08/2026, between **21:40 and 22:02 UTC** — the times recorded on the first
and last job of this run — against the local `resoiltwin` database, against the Climate
Data Store and against the IPMA open data feed. Nothing was carried over from the
tests: the tests for this layer do not touch the network, and the only real calls to
the two sources are the ones in this note.

The starting code was commit `f93c2a6` ("fix: only fail the ipma job when the run wrote
nothing at all"). **Two fixes were made during this run**, both because of what it
showed, and they are described below in the section *"Two defects only the real run
revealed"*.

---

## What this note confirms, and what it does not

**It confirms:** that the route `POST /sites/{code}/weather/sync` runs against both
real sources; that the reanalysis authenticates against the Climate Data Store,
submits, polls, downloads and reads the grid cell containing the site; that the IPMA
client picks the station nearest to the site and writes its hourly readings; that both
write with full provenance, distance included; that each run leaves a row in
`ingestion_jobs` with its `status`; that re-running writes no new rows; and that the
`/timeseries` route, for the same site and the same metric, returns **all three
provenances at once**.

**What it does not confirm, and this has to be said before any number:**

1. **Neither of these two sources measures on the parcel.** The station nearest to
   Turcifal is 5.34 km away; the reanalysis cell containing the site is 11.1 km north
   to south by 8.6 km east to west, and its centre is 5.41 km from the site. Every row
   of both series carries `measured_at_site: false`, and carries it because it is true.
2. **This is not validation.** It is the first time two scales cover the same day in
   this project. See the section *"The three provenances side by side"* — and above
   all, see how many days that really is.
3. **There is no water balance.** Reference evapotranspiration is not ingested in this
   phase, and without it none of these numbers converts into a statement about water in
   the soil.

## Two defects only the real run revealed

The tests for this layer all passed — 422 of them — and neither of the two defects below
had any way of appearing in them, for different reasons, both instructive.

### 1. The CDS zip was read only as far as the first file

AgERA5 delivers each month as a **zip with one `.nc` per day**. The reader extracted
`members[0]` and read only that one — one day per zip, meaning one day per variable per
month. The consequence, measured:

| | |
|---|---|
| days requested | 60 (01/07–29/08) |
| days the source had to give | **53** (01/07–22/08; see defect 2) |
| days read | **2** — 2026-07-01 and 2026-08-01 |
| rows written | **6** of 159 available |
| job status | `succeeded`, `error: null` |

The only days in the database after jobs 1–2 were those two, one row per metric.
**Nothing flagged the problem**: the job said `succeeded`, the `error` was `null`, and
`rows_written: 6` is the only clue — a low number does not raise its hand on its own.
The 153 rows jobs 5–6 wrote afterwards, without the request changing by a comma, are the
exact measure of what had been lost.

The test that existed (`test_agera5_daily_reads_a_zipped_download`) wraps **one** file in
a zip and proves that the zip path opens. It does not prove that the zip is read to the
end; those are two different claims and only the first was covered.

Fixed: all `.nc` members are read, in order, with the extraction name prefixed by the
index (two members in different folders can share a name). Two new guards: members that
select **different cells** are refused, because the cell signs the whole series and the
distance stored on every row depends on it; and a **repeated day** across two members is
refused, because which of the two values survived would otherwise depend on the order of
the zip members. Four new tests, none of which touches the network.

### 2. The job declared the requested window, not the covered one

Found straight afterwards, counting the rows from jobs 5–6: 53 days per metric, not 60.
**AgERA5 has a publication lag.** On 29/08/2026 the archive ended at **22/08**; 23 to 29
August did not yet exist anywhere.

This **is not a defect of ours and is not an error of the source** — it is what a
reanalysis archive is. Failing the job over it would fail every ingestion close to the
present, which is precisely the one that matters. The defect was elsewhere: the job went
on declaring `date_to: 2026-08-29`, meaning the job row claimed to cover seven days that
are not in the database and are not anywhere.

`sync_ipma` was already doing the right correction — narrowing the declared window to the
instants it actually brought back — and `sync_reanalysis` now does the same. The guard
`_garantir_dentro_da_janela` already refused the symmetric case (days **too many** in the
response); what was missing was telling the truth about days **too few**. Jobs 7 and 8,
in the table above, are that correction working against real data.

## The three provenances side by side

The query asked for, through `/timeseries`, with no provenance filter:

```
GET /api/v1/sites/EUC-TUR-01/timeseries?metric=air_temperature

point_count : 82
source_types: ["observed_screening", "reanalysis", "weather_observed"]

  observed_screening    5    2026-08-22 13:37 .. 2026-08-24 12:48   (instantaneous)
  reanalysis           53    2026-07-01 00:00 .. 2026-08-22 00:00   (24-hour mean)
  weather_observed     24    2026-08-28 22:00 .. 2026-08-29 21:00   (hourly)
```

**All three coexist, and that is what this query demonstrates.** The field probe held on
the parcel, the station 5.34 km away and the 11.1 × 8.6 km grid cell all answer the same
question, in the same response, each point saying what it is. Nothing merges them,
nothing averages them, nothing prefers one. For the other metrics the picture is the same
with fewer origins: `relative_humidity` has field and station (the reanalysis does not
ingest humidity in this phase), `precipitation` and `solar_radiation` have reanalysis and
station, `wind_speed` has only station.

### And now the part this task's plan assumed and the data contradicts

The plan expected to put all three side by side on the campaign days, 22 to 24 August.
**It cannot be done, and the reason is the two windows above:**

| pair of origins | days in common |
|---|---|
| field × reanalysis | **1** — 22/08 only. The reanalysis ends on 22/08 (publication lag) |
| field × station | **0** — the campaign is 22–24/08 and the station only has 28–29/08 |
| station × reanalysis | **0** — for the same reason, at both ends |

There is exactly **one day** in the whole system on which two of these scales overlap,
and it is two, never three. Here it is:

| origin | instant (UTC) | value | what the number is |
|---|---|---|---|
| `observed_screening` | 2026-08-22 13:37 | **30.0 °C** | instantaneous reading, screening probe, plot TUR-CANOPY |
| `observed_screening` | 2026-08-22 17:05 | **25.0 °C** | the same, three and a half hours later |
| `reanalysis` | 2026-08-22 (day) | **20.1300 °C** | 24-hour mean over the 11.1 × 8.6 km cell |

And the two remaining campaign days, so that what is missing is visible:

| day | field | reanalysis | station |
|---|---|---|---|
| 22/08 | 30.0 °C (13:37), 25.0 °C (17:05) | 20.1300 °C | — |
| 23/08 | 24.0 °C (07:00) | **not published** | — |
| 24/08 | 26.0 °C (12:48), on both plots | **not published** | — |

> ### ⚠️ What these numbers do **not** allow anyone to conclude
>
> **Nothing about agreement.** Neither in one direction nor the other.
>
> The three rows in the table above **are not the same quantity measured three times**.
> The field reading is one instant, at one point, with an uncalibrated screening probe.
> The reanalysis value is a **24-hour mean** — it includes the small hours — over a cell
> of 95 km². A reading taken at the hottest hour of the day and the mean of the whole day
> would be different numbers even if the instrument were perfect and standing in the same
> place. The difference between them is not error in anything.
>
> This note therefore **does not publish** — and nobody should derive from it —
> correlations, mean errors, bias, agreement percentages, or any goodness-of-fit
> statistic. There is no sample here: there is **one day**, and nothing is fitted on one
> day. Even with the three days the plan expected, nothing would be fitted on three.
>
> This project has already paid for not respecting that line. The note
> [`2026-08-29-mascara-scl.md`](2026-08-29-mascara-scl.md) documents **three wrong
> claims** produced by exactly this temptation, and records that the retraction of the
> first one was also wrong — the conclusion was right, the indicator it rested on did not
> decide the case. The lesson that stayed is about the reasoning, not about that one
> number: *when two values look close, or look far apart, both seem to be saying
> something, and neither is.*
>
> What these numbers **do** allow is what the previous section says: that the three
> provenances exist, coexist within the same metric at the same site, and reach the reader
> separated. That is a claim about the plumbing, and it is the only one this task had to
> make.

> **On the values withheld above — and on what withholding them achieves.** The parcel
> coordinates do not go into this document. That much is true, and it is the rule the
> three earlier notes follow too.
>
> It is not, however, true that this document does not locate the parcel, and the
> sentence that used to stand here said it did. Two things defeat the redaction. The
> first is in this note: a **named public station** and a **distance to it** place the
> site on a circle, and for `EUC-PTO-01` that circle has a radius of 0.89 km — some
> 2.5 km², a handful of parcels. The second is worse and is not in this note at all: the
> test suite of this repository has carried the canonical site point at full precision
> since its first commit, and the `EUC-TUR-EO1` box appears verbatim as a test fixture.
> Redacting prose while the fixtures publish the coordinate is not a safeguard; it is
> the appearance of one.
>
> So what stays here stays on its merits, not because it is harmless: the **distances**
> (5.34 km to the station, 5.41 km to the grid node), the **cell footprint** (11.1 km NS
> × 8.6 km EW), and the station identity. They carry the provenance argument. They also
> bound the site, and anyone deciding where this material may travel should weigh both.
> See `2026-09-03-the-rule-the-repository-did-not-keep.md`.

Three things to read there carefully:

- **`cell_size_km_ns` and `cell_size_km_ew` are two numbers and not one.** 0.1 degree is
  11.1 km north to south at any latitude, but only 8.6 km east to west at 39° (8.4 km at
  41.2°, at Porto). A single "cell size" would be the north–south value presented as the
  side of the cell — 22% above the real one in the wrong direction, stored on every row
  of the series.
- **`area_requested` is much larger than `area_aoi`**, and it is transport, not
  measurement: the CDS refuses a box smaller than the cell with
  `MultiAdaptorNoDataError`, so we ask for 0.4 degrees of side and read **one** cell —
  the one containing the site. The mean over the box would be ~2000 km², the size of a
  district, with a `cell_size_deg: 0.1` beside it describing something else.
- **`site_point_source: "aoi_centroid"`.** `site_lat`/`site_lon` read like a coordinate
  surveyed at the site and are not: they are the centroid of the area-of-interest
  polygon, computed. The `sites` table has no geometry.

### The two stations chosen

| site | station | id | distance |
|---|---|---|---|
| EUC-TUR-01 | Torres Vedras, Dois Portos | 1210739 | **5.34 km** |
| EUC-PTO-01 | S. Gens | 1210649 | 0.89 km |

222 stations were considered in both cases, with a 50 km ceiling. **None of them is
inside a parcel**, and 0.89 km is no exception to that — the `measured_at_site`
distinction is binary on purpose, and Porto's short distance is still an instrument
somewhere else.

Zero night-time radiation readings were discarded at **these two** stations. Some were
discarded at others: the client publishes the count per station when it cleans the feed,
and in this run it was **7 stations and 39 readings** — 2, 3, 3, 7, 8, 8 and 8
respectively — with values up to **185.3 W/m² at 03:00 UTC** at station 1210973. None of
those seven is the Turcifal or the Porto station, and that is why
`night_radiation_dropped` on the stored rows is 0: the counter refers to the station of
the row, not to the whole feed. If it referred to the feed, a zero would stop meaning
"this station is clean".

## Known limits, and none of them is solved in this phase

**Of the observed source:**

- **The IPMA series starts today.** The source has no archive: it publishes the last 24
  hours and nothing else. This project's observed history begins on 28/08 at 22:00 UTC
  because that is when the sync first ran, and not because anything happened at that
  instant.
- **There is no scheduling in this phase.** The sync is triggered by hand. Of every 24
  hours read, 23 are already there and are not written again — which is what would allow
  this to run hourly — but nothing runs it. **The series will have gaps**, and this is
  written here rather than discovered when someone goes looking for an hour that does not
  exist.
- **A source that has stopped is not detected.** If IPMA stops publishing, the series
  stops growing in silence. There is nothing comparing what should have arrived with what
  did.

**Of the reanalysis archive:**

- **AgERA5 lags by about a week.** Confirmed in this run: 29/08 requested, 22/08
  delivered. Any window ending near the present comes back short, and the job now says
  how far it got — but whoever asks for the last few days will not have them.
- **Reference evapotranspiration is not ingested.** It is within the scope of the layer
  and was the reason for choosing AgERA5 over ERA5-Land, but it is left for Phase D,
  which is what consumes it.
- **Hourly ERA5-Land is implemented in the client and not ingested.** Daily AgERA5 is
  enough for the water balance; the sub-daily one comes in when it is needed.

**Of the system, and not of the sources:**

- **Nobody looks at `ingestion_jobs.status`.** There is no alerting at all. A failed job
  is as silent as a misleading success — and jobs 1 and 2 of this note show that a
  misleading success is something that really happens.
- **Twilight is not protected.** Radiation is discarded with the sun below −6°; between
  −6° and 0° it passes. That is a choice, not an oversight: there is real light in that
  band and a cut there would discard true measurements.
- **The route is synchronous.** A reanalysis synchronisation holds the connection for
  minutes (four to five, measured here). The limit is the 15-connection `QueuePool`.
- **No authentication on the routes.** As in Phase B: the API must not be exposed
  publicly at this stage. Anyone reaching the route spends CDS quota.
