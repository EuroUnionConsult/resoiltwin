This note records an end-to-end verification made from scratch, with the database
recreated (`docker compose down -v`), at commit
`21d4ad9f423a2e9e8d8cc5f07ceffddfed6af2a5` ("fix: make the provenance guards bite on
the write path production uses"), which is the last code commit of this round. The
note itself is the only change made after it.

Every output below was collected in this run. Nothing was carried over from the
previous version of this note.

The point is to let anyone reproduce exactly what follows and confirm the numbers for
themselves — nothing here was copied from an earlier run, and nothing was invented.

## What this note confirms, and what it does not

It confirms: that the database comes up, that the five Alembic migrations apply
without error and survive a full `downgrade base` → `upgrade head` cycle, that the
field seed loads the 27 Turcifal screening readings plus the 4 derived VPD values
idempotently, that the test suite passes in full against a schema built by the
migrations, that the database refuses provenance values outside the enums, and that
the API serves those series over HTTP exactly as they were loaded.

**What it does not confirm, and this has to be said explicitly: no Copernicus data was
acquired in this phase.** Every observation in the system is `observed_screening`,
from an uncalibrated screening instrument (DUO TERRA, `calibration_status =
uncalibrated`), plus 4 `derived` values computed by the Tetens equation from
temperature and relative humidity — not measured directly. There is no satellite data,
there are no calibrated sensors, there is no agronomic validation, and the API has no
authentication — it must not be exposed publicly at this stage.

The schema produced by this path is byte for byte identical to the one produced by
`Base.metadata.create_all` — compared with `pg_dump --schema-only` over the six tables,
on two databases each built from scratch by one of the two paths:

```
$ wc -c /tmp/schema_mig.sql /tmp/schema_models.sql
   13481 /tmp/schema_mig.sql
   13481 /tmp/schema_models.sql

$ diff /tmp/schema_mig.sql /tmp/schema_models.sql && echo "SCHEMAS BYTE-IDENTICAL"
SCHEMAS BYTE-IDENTICAL
```

The `wc -c` is not decoration. On the first attempt at this comparison the two
`pg_dump` runs used `-t observations` without qualifying the schema, found no table at
all, and the `diff` of two empty files answered `SCHEMAS BYTE-IDENTICAL`. A diff only
proves something once you have confirmed that it compared something.

This comparison is no longer the main guarantee of parity; it is now one confirmation
among others. The guarantee lives in `tests/test_schema_parity.py`, which runs on every
pass of the suite: for each `CheckConstraint` declared in the models it verifies that
the database built by the migrations holds a constraint with the same name and an
equivalent definition, and in the other direction that the database holds no constraint
the models do not declare. Both definitions are normalised by PostgreSQL itself
(`pg_get_constraintdef`), so that what is compared is what the engine understood of
each one, and not two hand-written strings.

This is necessary because Alembic 1.13's autogenerate **does not compare
CheckConstraints**: a constraint changed in the model and forgotten in the migration
does not appear in `alembic revision --autogenerate` and only shows up on the first
database built from scratch.

## Real output — auditing a derived value backwards

Each VPD stores in `derived_from` the identifiers of the two observations that produced
it. The chain can be walked in the database:

```
$ VPD 2026-08-22T13:37:00+00:00 = 2.9701 kPa
  derived_from = ['9ebc4d17-3660-45b6-824c-58d772e0f920', '22d1bba4-8988-4e31-aaa1-e5f14b0e04c2']
  -> 9ebc4d17-3660-45b6-824c-58d772e0f920 air_temperature = 30.0 degC (observed_screening, valid)
  -> 22d1bba4-8988-4e31-aaa1-e5f14b0e04c2 relative_humidity = 30.0 percent (observed_screening, valid)
```

`es(30 °C) × (1 − 30/100) = 2.9701 kPa` — the stored value reproduces from the two
source readings. The test
`test_vpd_can_be_audited_back_to_the_measurements_that_produced_it` walks this path for
all four VPD values and recomputes each one.

## The shape of the censoring coherence rule, and its known limitation

The constraint `ck_censoring_flag_matches_qualifier` is a **one-way implication**, not
an equivalence: a saturated `quality_flag` forces a censored `value_qualifier`, and
`quality_flag = 'range_value'` forces `value_qualifier = 'range'`. The converse is not
imposed.

The reason is that the two fields measure orthogonal axes — `quality_flag` is a quality
assessment, `value_qualifier` is the semantics of the value. In the biconditional form
this constraint had before, a censored value with `quality_flag = 'unchecked'` was
refused; and `unchecked` is the model's own default. That made it impossible for an
ingestion job to write a top-of-scale reading before having assessed it, which is
exactly what the next phase does — it writes through server-side jobs, not through
`POST`. The 31 seed rows satisfy the new form: 4 saturated and 4 pH readings make the
antecedent true, the other 23 leave it empty.

What it **cannot** do is detect a reading that saturates at the top of scale but is
submitted as `exact` + `valid`: the database does not know that 2000 is that
instrument's ceiling for that metric. `instruments.scale_max` exists, but it is a single
value on a multi-parameter instrument — using it as a saturation threshold for every
metric would be semantically wrong (a temperature and a light reading do not share a
scale). Closing this gap requires per-metric scale limits, which is modelling work, not
another constraint.

## What this note supports

This note supports: there is a working end-to-end pipeline — PostGIS database,
versioned and reversible migrations, FastAPI API, and 27 real Turcifal field readings
ingested and served with explicit source type and provenance, with the provenance
vocabulary enforced by the database itself, each derived value linked to the
measurements that produced it, and 111 automated tests passing against the same schema
production will have — including a parity test that compares, constraint by constraint,
the schema declared in the models with the schema the migrations build. This note does
**not** support: integration with satellite data, calibrated sensors installed,
agronomic validation of the values, or an API ready for public exposure.
