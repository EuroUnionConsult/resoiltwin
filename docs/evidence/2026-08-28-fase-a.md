# Evidência — Fase A, backend de dados reais (28/08/2026)

Esta nota regista uma verificação de ponta a ponta feita a partir do zero,
com base de dados recriada (`docker compose down -v`), no commit
`21d4ad9f423a2e9e8d8cc5f07ceffddfed6af2a5` ("fix: make the provenance guards
bite on the write path production uses"), que é o último commit de código
desta ronda. A própria nota é a única alteração feita depois dele.

Todos os outputs abaixo foram recolhidos nesta execução. Nada foi reaproveitado
da versão anterior desta nota.

O objectivo é permitir a qualquer pessoa reproduzir exactamente o que se
segue e confirmar por si os números — nada aqui foi copiado de uma execução
anterior nem inventado.

## O que esta nota confirma, e o que não confirma

Confirma: que a base de dados sobe, que as cinco migrações Alembic aplicam
sem erro e sobrevivem a um ciclo completo `downgrade base` → `upgrade head`,
que o seed de campo carrega as 27 leituras de rastreio de Turcifal mais os 4
valores de VPD derivados de forma idempotente, que a suite de testes passa na
íntegra contra um schema construído pelas migrações, que a base rejeita
valores de proveniência fora dos enums, e que a API expõe essas séries via
HTTP tal como foram carregadas.

**Não confirma, e é importante dizê-lo explicitamente: nenhum dado
Copernicus foi adquirido nesta fase.** Todas as observações no sistema são
`observed_screening`, de um instrumento de rastreio não calibrado (DUO
TERRA, `calibration_status = uncalibrated`), mais 4 valores `derived`
calculados pela equação de Tetens a partir de temperatura e humidade
relativa — não medidos directamente. Não há dados de satélite, não há
sensores calibrados, não há validação agronómica, e a API não tem
autenticação — não deve ser exposta publicamente nesta fase.

O schema produzido por este caminho é byte a byte igual ao produzido por
`Base.metadata.create_all` — comparado com `pg_dump --schema-only` sobre as
seis tabelas, em duas bases construídas de raiz por cada um dos caminhos:

```
$ wc -c /tmp/schema_mig.sql /tmp/schema_models.sql
   13481 /tmp/schema_mig.sql
   13481 /tmp/schema_models.sql

$ diff /tmp/schema_mig.sql /tmp/schema_models.sql && echo "SCHEMAS BYTE-IDENTICOS"
SCHEMAS BYTE-IDENTICOS
```

O `wc -c` não é decoração. Na primeira tentativa desta comparação os dois
`pg_dump` correram com `-t observations` sem qualificar o esquema, não
encontraram tabela nenhuma, e o `diff` de dois ficheiros vazios respondeu
`SCHEMAS BYTE-IDENTICOS`. Um diff só prova alguma coisa depois de se
confirmar que comparou alguma coisa.

Esta comparação deixou de ser a garantia principal de paridade e passou a ser
uma confirmação a mais. A garantia está agora em `tests/test_schema_parity.py`,
que corre em cada execução da suite: para cada `CheckConstraint` declarada nos
modelos verifica que existe na base construída pelas migrações uma constraint
com o mesmo nome e definição equivalente, e no sentido inverso que a base não
tem nenhuma constraint que os modelos não declarem. As duas definições são
normalizadas pelo próprio PostgreSQL (`pg_get_constraintdef`), de forma a
comparar o que o motor entendeu de cada uma e não duas strings escritas à mão.

Isto é necessário porque o autogenerate do Alembic 1.13 **não compara
CheckConstraints**: uma constraint alterada no modelo e esquecida na migração
não aparece em `alembic revision --autogenerate` e só se manifesta na primeira
base construída do zero.

## Forma da coerência de censura, e a sua limitação conhecida

A constraint `ck_censoring_flag_matches_qualifier` é uma **implicação num só
sentido**, e não uma equivalência: `quality_flag` saturado obriga a
`value_qualifier` censurado, e `quality_flag = 'range_value'` obriga a
`value_qualifier = 'range'`. O recíproco não se impõe.

A razão é que os dois campos medem eixos ortogonais — `quality_flag` é uma
avaliação de qualidade, `value_qualifier` é a semântica do valor. Na forma de
bicondicional que esta constraint teve antes, um valor censurado com
`quality_flag = 'unchecked'` era rejeitado; e `unchecked` é o valor por
omissão do próprio modelo. Isso tornava impossível um trabalho de ingestão
gravar uma leitura no topo de escala antes de a ter avaliado, que é
exactamente o que a fase seguinte faz — escreve por trabalhos do lado do
servidor, não por `POST`. As 31 linhas do seed satisfazem a forma nova: 4
saturadas e 4 de pH tornam o antecedente verdadeiro, as outras 23 tornam-no
vazio.

**Não** consegue detectar uma leitura que satura no topo de escala mas é
submetida como `exact` + `valid`:
a base não sabe que 2000 é o tecto daquele instrumento para aquela métrica.
`instruments.scale_max` existe, mas é um valor único num instrumento
multi-parâmetro — usá-lo como limiar de saturação para todas as métricas
seria semanticamente errado (uma temperatura e uma leitura de luz não
partilham escala). Fechar esta lacuna exige limites de escala por métrica,
que é trabalho de modelação, não uma constraint.

## O que esta nota sustenta

Esta nota sustenta: existe uma pipeline funcional de ponta a ponta —
base de dados PostGIS, migrações versionadas e reversíveis, API FastAPI e 27
leituras de campo reais de Turcifal ingeridas e servidas por `source_type` e
proveniência explícitos, com o vocabulário de proveniência imposto pela
própria base de dados, cada valor derivado ligado às medições que o
produziram, e 111 testes automatizados a passar contra o mesmo schema que a
produção vai ter — incluindo um teste de paridade que compara, constraint a
constraint, o schema declarado nos modelos com o schema que as migrações
constroem. Esta nota **não** sustenta:
integração com dados de satélite, sensores calibrados instalados, validação
agronómica dos valores, ou uma API pronta para exposição pública.
