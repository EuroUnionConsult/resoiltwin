# Evidence — Phase D, water balance (30/08/2026)

> *Written in Portuguese on 30/08/2026, translated into English on 01/09/2026. The
> English text is the normative version of this note; the Portuguese original stands
> unchanged in the repository history at commit `bf3fd90`. This note publishes no parcel
> coordinates; that redaction is preserved.*

**This is an exercise in plumbing, not an agronomic estimate.** What this note records is
that a derived series crosses the whole system — it enters through the two weather series
that were already in the database, passes through a pure model, and comes out stored with
full provenance and `source_type = simulated` — and **not** that the numbers that came out
say anything about the water in these soils. The reasons are all in the next section, and
the first of them is enough on its own: **the available water capacity of this ground has
not been measured by anyone, there is not one soil analysis of these sites in this project,
and that is the parameter that dominates the result.** Making it mandatory and declared
made it **auditable, not true**.

Run on 30/08/2026, between **08:27 and 08:39 UTC** — the times recorded on the first and
last job of this run — against the local `resoiltwin` database and, in the first half,
against the Copernicus Climate Data Store. The starting code is commit `fded5d8`
(`chore: record the mutation round for this lot`), with the route
`POST /sites/{code}/water/sync` already in place.

---

## What this note does not say, and cannot say

Four gaps, all of them known before the run and none of them closed by it.

1. **The available water capacity is not measured.** It enters as a mandatory argument in
   the request body, travels in the `processing_version` (and therefore in the row's
   identity) and in each observation's `evidence`, beside `capacity_is_measured: false`.
   Anyone reading a row knows exactly which number produced it, and knows that number was
   chosen. It is still chosen.
2. **There is no crop coefficient (Kc).** The model consumes **reference**
   evapotranspiration exactly as the source publishes it, and draws no distinction between
   reference and actual evapotranspiration. Applying a Kc without having measured it in the
   field would be adding a second invented number to the first.
3. **The initial state of the reservoir is not known.** See the section *"Why the output is
   a range"*.
4. **None of the inputs is measured on the parcel.** They come from a reanalysis cell of
   11.1 km north-south by 8.6 km east-west, and each row of the output series inherits
   `measured_at_site: false` from
   the inputs and adds its own.

**There is no claim in this note about water stress, about irrigation need, about the state
of any crop, nor any comparison with what would be "expected".** That is not writerly
caution: nothing that was run authorises any of those sentences, and the note of 29/08 on
the SCL mask (`docs/evidence/2026-08-29-mascara-scl.md`) is the record of what happens in
this project when that temptation is given in to — three wrong claims, and the retraction
of the first one was also wrong.

## Why the output is a range, and not a number

**This is the most defensible decision of this phase and also the least obvious**, and it is
worth explaining to the reader before looking at any value.

A reservoir balance needs to know how much water was there on day one. Nobody knows. There
are three ways out and two of them invent:

- **receive it as an argument** adds a second number nobody measured to the first number
  nobody measured;
- **assume it** — full, or empty — is picking it by hand and then forgetting it was picked;
- **not choose.** This was the one.

Each series is run **twice**, from the only two extremes the reservoir admits (empty and
full), and what is stored is the range between the two trajectories. Any true starting state
lies between them, every day, because the daily step is monotonic in the state — verified by
a test against an independent oracle, in `tests/test_water_balance.py`.

And the range **closes itself**: as soon as the two trajectories touch the same limit they
become the same, bit for bit, and from then on the value **no longer depends on what nobody
measured** — it depends only on the inputs. That day and the ones after it come out as
`value_qualifier = 'exact'`; the earlier ones come out as `'range'`, with
`value_min`/`value_max` filled and `value_numeric` at NULL. No new column was needed: the
`CHECK` that requires the pair to be filled has existed since migration 0004.

**The model admits ignorance for exactly as long as it exists, and stops admitting it when it
goes away.**

## The three capacities: chosen, not measured

None of the three describes these soils, because there is nothing in this project that
describes these soils. They were chosen to make visible **the model's own sensitivity to the
parameter nobody measured**, and each is declared in the identity of the rows it produced:

- **100 mm** — the capacity with which this phase's test suite exercises the whole path.
  Running against the database the same number the tests run avoids what is in production
  being the one value never tried.
- **50 mm** and **250 mm** — below and above, to show the effect. 250 mm was chosen for
  sitting next to the threshold Task 2 had predicted by reasoning and that this run confirms
  with numbers.

### How many days came out determined, and how many did not

| site | capacity | determined | undetermined | 1st determined day |
|---|---|---|---|---|
| EUC-TUR-01 | 50 mm | **47** / 53 | 6 | 2026-07-07 |
| EUC-TUR-01 | 100 mm | **37** / 53 | 16 | 2026-07-17 |
| EUC-TUR-01 | 250 mm | **10** / 53 | 43 | 2026-08-13 |

⚠️ **The larger the chosen capacity, the later the range collapses — and at Porto, with
250 mm, the whole 53-day series stays undetermined.** There is not one day on which the value
stops depending on the initial state nobody knows, and all 53 rows stay as ranges.

### ⛔ And the table above misleads anyone who reads it without this

**The 174 determined values are all exactly `0.0000 mm`** — one single distinct value in the
whole column. **All 318 lower bounds are `0.0`.** Verified in the database, not deduced.

What happened is that **it did not rain**:

| site | rain, 53 days | ET0, 53 days | rain / ET0 |
|---|---|---|---|
| EUC-TUR-01 | **3.48 mm** | 303.95 mm | **1.1 %** |
| EUC-PTO-01 | **10.69 mm** | 256.97 mm | **4.2 %** |

And it is not only the total. At Turcifal **the wettest day never reaches the least-thirsty
day**: the daily maximum rainfall is 0.80 mm against a daily minimum ET0 of 3.61 mm. At Porto
it does, on one day out of fifty-three — 3.35 mm against 3.22 mm — and on no other. The trajectory starting from the empty
reservoir **never leaves zero**.

So **every collapse happened on the floor, none on the ceiling**. "47 of 53 determined" reads
like two trajectories converging; what happened was the upper one descending until it hit the
floor where the lower one already was. It is July and August in Portugal, and the result is in
no way surprising — but **the table on its own suggests a model working over variation that
did not exist in this data.**

What this means for a reader: this run **did not exercise the model**. It exercised the path.
The two halves that do the real work — the overflow and the cut across a gap in the series —
are still defended by tests and by mutants, and **not by a real run**. A winter window would
say far more.


**That is not a defect: it is ignorance showing.** A larger reservoir takes longer to empty
itself or to fill completely, and while neither of the two extreme trajectories reaches a
limit, the difference between them does not shrink. The alternative — storing a number — would
only be possible by choosing an initial state, that is, by hiding with a hand-picked value
exactly the ignorance the table above shows.

### Two things this run did not exercise

Saying so now is cheaper than finding out later:

- **No day overflowed.** The runoff stored is 0.00 mm on all 318 rows, across the three
  capacities and both sites. The model's overflow branch, which the suite defends with tests
  of its own, **was not touched by real data** in this run.
- **There was no gap in the series.** All 318 rows have `segment: 0`: the two inputs cover the
  same 53 contiguous days, so the segment cut — the other design decision of Task 2 — was not
  exercised by real data either.

## A 202 is not success

The route returns **202** when the request has been accepted and processed, and the outcome is
in the body's `status` — not in the HTTP code. **Job 10** exists to demonstrate that against
the real database: a window from 01/09 to 10/09, for which there is not one single input row.

```
HTTP 202
{"status": "failed", "rows_written": 0, "date_from": "2026-09-01", "date_to": "2026-09-10",
 "error": "ValueError: Nao ha uma unica linha de 'precipitation' para este sitio em
           [2026-09-01, 2026-09-10]. O balanco precisa das duas series de entrada; tratar a
           que falta como zero era afirmar que nao choveu nada, ou que nao houve procura de
           agua nenhuma, em dias que ninguem observou. …"}
```

The stored error message is quoted verbatim, in the Portuguese in which the code writes it: it
says that there is not one row of `precipitation` for this site in that window, that the
balance needs both input series, and that treating the missing one as zero would be claiming
that no rain fell at all, or that there was no demand for water at all, on days nobody
observed.

**A client that reads only the `202` concludes the series was stored.** It was not. It is the
same form of defect that Phase C recorded with a `succeeded` job declaring a window it did not
cover, and the reason `restore_dev_data.py` had to start reading each job's `status`.

The refusals that happen **before** there is a job come out as HTTP errors and leave no trace
in the database. Verified in this run, against the real database:

| request | response | job created |
|---|---|---|
| `available_water_capacity_mm: 0` | **422** | none |
| site `NAO-EXISTE` | **404** | none |
| window with no inputs | **202** with `failed` | yes, and it is the record |

## What is left to do, and what is worrying

**Of the domain, and this is what weighs most:**

- **The available water capacity is still unmeasured.** Until somebody measures it, what comes
  out is a series consistent with the inputs, and nothing more. A soil analysis of these two
  sites changes the status of this whole phase; nothing done in the code substitutes for it.
- **No Kc and no distinction between ET0 and actual ET**, declared out of scope in the plan
  and repeated here.
- **The inputs come from a cell of 11.1 km north-south by 8.6 km east-west.** Two parcels
  inside the same cell receive
  exactly the same rain and the same ET0.

**Of the system:**

- **Nobody looks at `ingestion_jobs.status`.** There is no alerting at all, and job 10 of this
  note stays in the database as proof that a `failed` is as silent as a success.
- **The overflow branch and the segment cut were not exercised by real data** — see above.
  They are defended by tests and by mutants, not by a run.
- **The route has no authentication**, like the others: the API must not be exposed publicly at
  this stage.
- **Running the balance three times with three capacities triples the rows.** It is the right
  design — two capacities are two series and not two runs of the same one — but anyone running
  this over a long series has to account for the cost.
- **The provenance of the inputs does not fit in the `processing_version`** and is therefore
  not in the row's identity, unlike the capacity. There is a guard that fails when a window is
  rewritten whose rows declare a different provenance, but it does not put the two series side
  by side.
